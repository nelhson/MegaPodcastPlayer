# ADD-3 — OPML

*8 September 2026. What was built for ADD-3 of `docs/reports/2026-09-07-ux-design-plan.md`, and the
four decisions taken while building it that the plan did not settle.*

---

## What it is

Two more rows in the settings screen's backup section: *Export subscriptions (OPML)* and *Import
subscriptions (OPML)*. The backup pair stays exactly as it was, above them.

Four rows where there were two, and the supporting lines are what make that legible rather than
confusing: *"Shows only, in the format other podcast apps read"* against *"Last backup: 7 September"*.
The two files answer different questions and the screen says which — the backup is how this app
survives a wiped database, and OPML is how twenty subscriptions arrive from another app or leave
for one.

## The one idea

**An OPML import is a restore of a backup the user never had.**

Everything an import must do beyond parsing — fetch twenty feeds one at a time, carry on past the
one that 404s and name it afterwards, survive the process being killed nine shows in, merge with
shows already present instead of duplicating them — the restorer does already, and it does it
because a restore has exactly the same shape. So the decoded OPML is turned into a `BackupFile`
carrying podcasts and nothing else, encoded, and handed to the same `LibraryRestorer`. `OpmlImport.kt`
is that conversion and is thirty lines; there is no importer.

The alternative was answering all of that a second time, and the two answers would have disagreed
the first time either changed.

## Four decisions the plan left open

**D-24 — Both halves live in Settings, next to the backup, not on the add-a-show screen.** The row
sits in §3.4 with ADD-1 and ADD-2, which are both about the Search screen — so the import could
have gone there. It did not. Import and export are one pair and belong within reach of each other,
and the question a user brings to Settings is "how do I get my library in and out", while the
question they bring to Search is "what is this one show called". Search adds a show; an import is
not that, and putting it there would make the add screen answer two questions.

**D-25 — An OPML export is not a backup, and must not reset the "last backup" line.** That line is a
warning about a database that is recreated rather than migrated. An OPML file cannot answer it: it
holds no positions, no queue, no downloads and no moments. Letting an export of it record a backup
would be the app telling the user they are safe at the exact moment they are not — so
`exportOpmlTo` writes the document and records nothing, and a test asserts the `recordExported`
that does not happen.

**D-26 — A YouTube show exports as `type="rss"` and imports back as YouTube.** The two are not in
conflict. A playlist's Atom feed genuinely *is* an XML document at an `http` URL, so writing
`type="rss"` is what lets an app that has never heard of this one subscribe to it. On the way back
in, the *URL* is asked rather than the attribute: `youTubePlaylistIdOrNull` is the exact inverse of
the feed URL this app minted when the playlist was added, so a library that leaves here as OPML
comes home as what it was rather than as a set of RSS shows that will not play.

**D-27 — Skipped rows are reported, not folded into the total.** An OPML file's `<outline>` elements
include folders, which have children and no `xmlUrl`, and — from a file that is broken or hostile —
rows this app refuses to fetch. Both are dropped, and the count is shown in the confirmation dialog
before anything happens. A file whose extra rows were folders is ordinary; one whose rows were
mostly refused is worth going back to the other app for, and a user cannot tell those apart from a
count of what arrived.

## Untrusted input, which is most of what the codec is

An OPML file is written by another program and picked out of a document provider. Three things
follow, and they are the parts of `OpmlCodec` worth reading:

- **External entities are off.** The attack is XXE: a document that declares an entity pointing at a
  local file, and gets the parser to fetch it and paste it into a show title. The hardening already
  existed for feeds in `RssParser`, whose own comment predicted this — *"any second XML source added
  here will need exactly the same treatment"* — so it moved to `:core:model/xml/SafeXml.kt`, which
  is the one module both parsers can see, and `RssParser` now calls it too. There is one
  `untrustedXmlParserFactory()` in this app, and both readers of foreign XML use it.
- **Only `http` and `https` feed URLs are accepted.** These URLs go straight to the app's own
  fetcher. A `file:///` row would make an import read the device's storage, and a `content://` row
  another app's, on the say-so of a file the user merely opened. This is the same rule
  `isPlayableMediaUrl` applies to audio, applied where *feeds* enter.
- **One document may contribute at most 1000 subscriptions.** Far past any real library, and low
  enough that a generated or hostile file cannot turn one tap into a hundred thousand feed fetches.

## Tests

- `OpmlCodecTest` (`:core:model`) — thirteen cases, mostly about other people's files: folders
  flattened, the same feed under two folders imported once, a missing title falling back to the feed
  URL, `text` winning over `title`, a namespaced document, a round trip through an ampersand, an
  empty library that still exports valid OPML, and both hostile shapes — an external entity pointed
  at a file the test writes so the assertion means the same thing on every platform, and a document
  larger than the cap.
- `OpmlImportTest` (`:feature:settings`) — five cases on the conversion: the synthetic backup
  carries no episodes, no queue, no downloads and no moments (a restore replaces the queue
  wholesale, so an import that carried an empty one would empty the user's); a YouTube feed URL
  comes back as a YouTube show; the document's order becomes the library's order, which is the only
  ordering information OPML has.
- `SettingsViewModelTest` (`:feature:settings`) — seven new cases: the suggested file name; an
  export that writes OPML and records no backup (D-25); a failed export reported as its own
  failure; a picked file held for confirmation and *marked* as OPML; confirming an import never
  re-downloading whatever it is passed; the JSON backup picked into the wrong row being refused;
  and an empty subscription list saying so rather than importing nothing.
- `SettingsScreenTest` (`:feature:settings`) — four new cases: the four rows and the descriptions
  that tell them apart, both new rows reaching their picker, and the dialog dropping the
  re-download switch for an OPML import while saying what will not arrive.

**What has no test.** The pickers themselves, which need an activity result registry — the same
reason the backup pair's launchers live in `SettingsRoute` and the stateless screen is what the
tests drive. And the goldens are unchanged: the settings screenshot captures the window, and the
backup section is below the fold.

## Not done here

**The device pass**, for the thing no test can reach: whether a real OPML file out of a real
podcast app — Pocket Casts, AntennaPod, Overcast — imports cleanly, and whether this app's export is
accepted by one of them. The codec is written against the format rather than against a sample, and
that is exactly the kind of confidence a file from somebody else's exporter is for.

**A share target for OPML.** ADD-1 made this app a share target for podcast *links*; an OPML file
arriving through the share sheet would be the same idea one step out. It is not in the plan and is
not scheduled — the row asked for import and export, and both are here.
