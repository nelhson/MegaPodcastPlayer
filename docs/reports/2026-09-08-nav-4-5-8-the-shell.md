# NAV-4, NAV-5, NAV-8 — three things every tab should have done already

*8 September 2026. The first of the unscheduled findings, taken as one batch because all three are
about the app's five top-level destinations and all three touch the same files.*

---

## What changed

**NAV-5 — the gear is on every top-level bar.** It was on the library's alone, which made settings a
tab switch plus a tap from four of the five screens. `SettingsAction` in `:core:designsystem` is one
glyph with one label, and Listen, Library, Downloads, Queue and Moments each carry it. An overflow
was the alternative and is worse: a menu holding a single item on four screens out of five is a
container invented to hide the one thing inside it (D-7).

**NAV-4 — re-tapping the tab you are on scrolls its list to the top.** `navigateToTopLevel` used to
return early and do nothing; it now *returns* whether it moved. The shell turns a `false` into an
incremented count, and every top-level screen watches that count through `ScrollToTopEffect`.

**NAV-8 — the empty library stops using a layout glyph to mean "no shows".** `GridView` says *grid*,
which is a way of arranging shows and not a way of having none. It is the `Podcasts` mark now — the
same one the artwork placeholder uses.

## Two decisions the batch needed

**D-32 — The re-tap is a count the shell owns, not a callback each screen registers.** Only the
shell knows a tap was a *re*-tap; only the screen owns a list. The narrow thing to pass between them
is the fact, and a count carries it where a boolean would not — the same request can be made twice,
and a flag that was already `true` the second time does nothing. `navigateToTopLevel` therefore
reports rather than acts: it cannot scroll a list, and inventing a registry of scroll callbacks for
it to call would put five screens' business inside a function about the back stack.

**D-33 — `ScrollToTopEffect` remembers the signal it arrived with.** This is the whole subtlety.
Every `LaunchedEffect` runs once on entering the composition, so a naïve version would scroll a tab
to the top *on arrival* — throwing away the scroll position the navigation library had carefully
saved on the way out. What a screen is reacting to is the signal changing **while it is up**, which
is precisely a re-tap and nothing else. Two tests state both halves, because only one of them is
visible in the happy case.

## What the goldens did not catch

Adding a 24 dp gear to four app bars changed no golden. The suite verified green, and only a
deliberate re-record showed the icon had appeared.

That is the tolerance working as designed and worth writing down anyway. `CHANGED_PIXEL_TOLERANCE`
is 1 % of pixels, calibrated so a Windows laptop and a Linux CI runner can disagree about glyph
antialiasing without failing every golden with a word in it. A 24 dp icon at mdpi is about 0.16 % of
a 411×891 image — comfortably underneath. The conclusion is not to tighten the number, which would
trade a real property (CI agreeing with a laptop) for a coincidence, but to stop expecting goldens
to answer a question they are not shaped for: **whether a control exists is a behaviour assertion,
not an image comparison.** That is what the three new screen tests do, and they would have failed
had the gear not been wired.

The goldens are re-recorded regardless, because an image that no longer shows what the screen shows
is worse than no image.

**The library's empty state had no preview at all**, which is how it kept a grid glyph for as long
as it did — DS-5 records every state that *has* a preview, and this one did not. It has one now, and
`library-empty` is three more goldens.

## Tests

- `TopLevelNavigationTest` (`:app`) — two new cases on the return value: re-tapping the tab under
  the finger reports `false` and moves nothing, and coming back to a tab further down the stack
  reports `true`. The second is the distinction that matters — a show is open over the library, the
  user taps Library, the show is dropped, and the list must *not* also be scrolled to the top,
  because they asked to see the library they left at the place they left it.
- `TopLevelActionsTest` (`:core:designsystem`) — three cases: the gear reports a tap and announces
  itself, a signal that changes while the screen is up scrolls to zero, and a screen that arrives
  already holding a signal scrolls nothing (D-33).
- `MomentsScreenTest`, `DownloadsScreenTest`, `QueueScreenTest` — one case each: the bar carries the
  gear and it reaches its handler. `LibraryScreenTest` already had one. Listen has no screen test —
  its gear is covered by its goldens, which is the weaker of the two and is said here rather than
  left implied.
- Three new goldens: `library-empty`.

## Not done here

**Listen's screen test.** The Listen tab is the app's start destination and has a view-model test
and goldens but no screen test. Adding one for a single assertion would be a file that exists to
hold one line; the next behavioural finding on that screen should bring it with it.
